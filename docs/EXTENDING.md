# 扩展与定制

这份文档回答一个问题：**别人想在 dsh-hello 上加自己的东西，什么时候改配置就够，什么时候必须 fork？**
它同时是官网 "高级 / 定制" 一节的文案底稿。

## 一句话判断

> **能"加"的用配套插件，要"减"的、要"换身份"的、要"换协议"的，才 fork。**

dsh 的路由是 composition 级契约：`webServer.register` 对重复的 `(kind, path)` 直接抛错，
已经挂上的能力也没法从外部撤掉。所以"收紧"和"改写"只能在插件内部做。

## 三层定制

| 层级 | 做什么 | 代价 |
|---|---|---|
| **配置** | 改配对码/锁定、审批归属、推送渠道、超时、`basePath`、限流 | 改一行 YAML |
| **配套插件** | 在旁边挂自己的 HTTP 路由、接自己的系统（导出、报表、Webhook） | 一个独立小包，不改 dsh-hello |
| **fork** | 改权限模型、身份体系、协议、客户端形态 | 自己维护一个发行版 |

配套插件能加不能减：它无法隐藏 `/sessions`、无法让 `/files` 只读、也无法替换配对流程。

## 什么场景真的需要 fork

### 1. 权限与可见性

现在的模型是"配对即全权"：任何配对设备都能看所有会话、所有工作区文件、开终端、答审批。

- **角色分级**：管理员能开终端和写文件；只读设备只能看会话；"审批设备"只能答复审批。
- **按工作区隔离**：A 团队只看 `a/`，B 团队只看 `b/`，终端 cwd 也受同一套规则约束。
- **临时访客**：给客户一个二维码，只读某个 session，到期自动失效。

对应改动：`routes.ts` 里 `auth: 'device'` 之后的授权层，以及 `sessions.ts` / `files.ts` / `terminal.ts` 的过滤。

### 2. 合规与审计

- 审批、文件下载、终端命令写入 SIEM，带设备身份与来源；
- 按文件名/内容阻断下载（`.env`、私钥），而不只是限制大小；
- 会话内容按策略裁剪后再下发，设定保留期与脱敏规则。

需要新增拦截点与审计账本。

### 3. 身份体系对接

- SSO / OIDC / LDAP 取代配对码，离职自动吊销；
- MDM 下发配置、设备证书、mTLS、IP 白名单；
- 推送走公司自建服务，而不是公共 relay。

对应改动：`devices.ts`、`pairing.ts`、`push.ts`。

### 4. 端不一样

- 自研 App / 小程序 / 桌面客户端，协议不是"配对码 + SSE + JSON"；
- 需要 WebSocket、protobuf 或 WebView 桥；
- 一个客户端聚合多台 Host。

### 5. 网络拓扑

- 放在公司网关后：Cookie/OAuth、路径改写、反代终止 TLS；
- 多租户共享一台 Host：每租户独立 `basePath`、设备表与配额；
- 内网离线：没有 npm、没有 GMS，推送只能用轮询。

### 6. 产品化

- 白标：自己的名字、引导、商店素材；
- 配额：每设备每天的 token/时长上限、上传大小上限；
- 计费与用量报表。

## fork 检查清单

| 位置 | 现值 | 改成 | 原因 |
|---|---|---|---|
| `package.json` `name` | `dsh-hello` | `@scope/dsh-hello` | npm 归属 |
| `cordis.patch.yml` | `id: dsh-hello` / `name: dsh-hello` | 你的 id / 你的包名 | `name` 必须是包名 |
| `src/index.ts` | `export const name = 'dsh-hello'` | 你的 id | Cordis 插件名 |
| 凭证键 | `dsh-hello/{devices,pairing,interactions,push}` | 你的前缀 | 否则与原版共用设备与配对 |
| `client/client.js` | 插件 `id: 'dsh-hello'`、i18n `NS` | 你的 id | 设置页与文案命名空间 |
| `basePath` | `/dsh-hello` | 见下一节 | 决定官方 App 能不能用 |

## 官方 App 还能用吗

这是 fork 的核心取舍，两条路：

| 路线 | `basePath` | App | 适合 |
|---|---|---|---|
| **替换** | 保持 `/dsh-hello` | 官方 DSH Hello 直接可用（探测 `/dsh-hello/health`，协议 1） | 只想换服务端实现 |
| **独立** | 改成自己的路径 | 需要自己的 App（探测路径目前只有 `/dsh-hello`，App 端尚未提供该设置） | 想做另一个产品 |

保持 `basePath` 与协议字段不变，官方便携端就是现成的。

## 为什么不能和原版并存

同一个 profile 里只能二选一：

- 路由重复：两个插件都挂 `/dsh-hello/*`，第二个加载时直接抛错；
- 凭证键冲突：设备表、配对状态、审批策略会被共用；
- 客户端设置页 id 重复；
- 首页注入的 `__DSH_HELLO__` 全局会互相覆盖。

## 发布与许可

- 仓库是 **MIT**：fork、改名、再发布都可以，保留 `LICENSE` 与版权声明；
- 建议同时改 README 的项目名与仓库地址，避免问题报到上游；
- `engines.dsh` 与运行时的 `dshVersionRange` 会校验 dsh 版本；
  跟进慢的 fork 在新版 dsh 上会明确拒绝加载，而不是静默出错。

## 给官网"高级"一节的呈现建议

1. **标题**：能改的、不能改的（Extending without forking）
2. **三栏**：配置 / 配套插件 / fork，各一句话 + 代价；
3. **一句判断**：加法用插件，减法才 fork；
4. **两个提醒**：不能与原版并存；保持 `basePath` 才能继续用官方 App。
